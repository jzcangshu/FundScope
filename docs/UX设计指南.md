# 基金估值分析看板：UX 设计指南

> 本文定义用户需要完成什么、系统必须让用户理解什么、关键交互应遵守哪些边界；不规定页面像素、组件库、具体视觉风格、前端框架或页面必须采用的布局。

## 0. 文档定位与使用方式

### 0.1 这份文档解决什么问题

基金估值看板的价值不是“把数字放到漂亮的页面上”，而是让内部人员能够在不确定性和时间压力下，快速回答四个问题：

1. 今天哪些产品的数据已经可信、覆盖到哪里、是否仍在处理？
2. 某个异常是数据错误、业务例外，还是系统尚未完成？我下一步该做什么？
3. 我看到的净值、收益和风险结论来自哪一份估值文件、哪个版本、哪个估值日？
4. 我执行发布、撤回、配置修改或清理后，影响是什么，能否复核和恢复？

设计应围绕上述问题组织认知路径，而不是围绕后端接口、数据库表或既有 Demo 页面复制界面。

### 0.2 事实来源和范围

当前代码与长期文档是行为事实来源：业务数据唯一来自估值 Excel（电子表格）；手工上传、邮件附件和历史迁移只是三种接入方式；前端不计算指标、不伪造数据、不绕过权限。现有正式页面和 API（接口）包括登录/初始化、公司总览、风险、产品列表与详情、导入、异常复核、邮件接入、产品/科目/风险规则配置、账号、审计、系统设置和数据保留。

下一版可以重排信息架构、合并页面、改变交互顺序和视觉语言，但不得把暂不提供的能力包装成已存在的事实。以下内容中的“必须”指用户体验和业务安全边界；“建议”指应优先验证的方向；“可选”指不影响业务正确性的设计自由度。

### 0.3 设计决策的优先级

当体验目标冲突时，按以下顺序取舍：

1. 数据可信度、权限和不可逆操作的安全性；
2. 用户能否理解当前状态并采取正确下一步；
3. 高频任务的速度、连续性和可恢复性；
4. 信息的可扫描性与精确查看能力；
5. 品牌表达、装饰和动效。

## 1. 产品与用户模型

### 1.1 产品定位

这是一个面向私募基金内部运营和管理层的估值数据治理与分析工作台。它连接“文件进入系统”与“管理层看到已发布结果”之间的链路：接收、识别、标准化、校验、人工复核、发布、分析、风险处理和审计追踪。

它不是交易终端、外部行情终端、投顾推荐工具或通用 BI（商业智能）模板。系统不应暗示自己拥有外部基准、交易流水、申赎流水、合同限额、行业穿透、VaR（风险价值）或精确交易归因等当前数据无法可靠支持的结论。

### 1.2 主要用户

| 用户 | 目标 | 典型压力 | 设计重点 |
| --- | --- | --- | --- |
| 管理层/只读用户 `viewer`（普通看板） | 快速判断公司与产品状态，查看趋势和开放风险 | 时间短，不想理解处理细节，但不能被错误的确定性误导 | 先给结论，再给覆盖、质量、分析状态和可追溯入口；只显示可读操作 |
| 业务员 `operator`（业务员） | 接收估值、处理异常、发布版本、处理风险、维护业务目录 | 每日重复操作，文件来源混杂，需在不破坏历史的情况下纠正配置 | 队列优先、批量但可控、异常有证据、写操作有原因、失败可恢复 |
| 系统管理员 `admin`（系统管理员） | 管理用户、邮件、规则、系统设置、备份和原始文件保留 | 低频高风险，后果可能跨全局或不可逆 | 强确认、预演、影响范围、审计、恢复路径和权限提示 |

不做产品级数据隔离：业务员和普通看板都可查看全部活动产品。角色只能决定能力，不应被视觉设计成不同产品或不同数据宇宙。

### 1.3 用户心智模型

用户应始终能把系统理解成一条有证据的流水线：

```text
文件来源 → 接收/去重 → 识别 → 解析/校验 → 可发布或待复核 → 发布/替代 → 分析就绪 → 看板与风险
```

页面可以用更自然的中文命名，但不能把“处理中”“待复核”“已发布”“分析过期”混成同一个“状态”。状态是事实，质量是判断，分析就绪是计算进度，三者需要在视觉和文字上分开。

## 2. 体验目标与成功标准

### 2.1 体验目标

- **一眼知道是否可信**：任何数据视图都先表达数据截至日期、发布版本、覆盖范围、质量状态和分析状态。
- **一条路径完成任务**：从发现问题到查看证据、作出决定、看到结果，不要求用户记住后端编号或跳来跳去。
- **风险可见但不制造噪声**：严重度、开放时间、影响产品和处理状态清楚；提示不应与阻断异常争夺同等注意力。
- **动作有后果预览**：发布、驳回、撤回、恢复、批量操作、规则修改、禁用账号和原始文件清理都要在动作前说明影响。
- **失败仍可继续**：网络失败、后台任务失败、并发冲突和权限不足都要说明当前事实、下一步和是否可以重试；不能只出现“操作失败”。
- **精致但克制**：金融数据是主角；视觉层次、留白、数字对齐和状态色服务于扫描，不用装饰掩盖质量或制造“实时交易”的错觉。

### 2.2 可验证的成功标准

设计评审和可用性测试至少应验证：

1. 新用户能在第一次登录后找到“今天有哪些产品可看、哪些还不能看”；
2. 业务员能从一个待复核版本定位到具体异常、原始文件和估值日，并能说出发布后会发生什么；
3. 用户能区分“没有数据”“数据未发布”“分析处理中”“分析过期”和“请求失败”；
4. 任何不可逆或高影响操作在确认前都能看见对象、范围、原因要求和恢复可能性；
5. 管理层只读用户不会被展示其无权执行的写操作；风险规则配置作为单独授权能力开放，风险事件处理仍不可用；
6. 键盘、屏幕阅读器、放大文字和窄屏用户能完成登录、筛选、查看详情和处理表单；
7. 设计不会承诺产品范围之外的指标，不会将缺失值默认为零，也不会把推断来源写成确定事实。

## 3. 信息架构原则

### 3.1 从用户任务而非技术模块出发

建议围绕四个稳定工作域组织导航或入口：

1. **看结果**：公司总览、产品、产品详情、风险；
2. **处理数据**：导入、复核、邮件接入；
3. **维护口径**：产品目录、别名、份额类别、科目映射、风险规则；
4. **管理系统**：账号、审计、系统设置、数据保留与备份。

具体是侧栏、顶部导航、工作台或其他模式由设计师决定，但同一层级不要混用多套导航范式。高频任务入口应稳定可达，深层页面要支持 URL（网页地址）直达和可预测返回。

### 3.2 共享上下文

除登录/初始化外，所有数据页应有稳定的上下文区，至少能回答：

- 当前页面/产品/估值日或日期范围；
- 数据截至何时；
- 当前读到的是哪个已发布版本；
- 覆盖率或可用产品数；
- 质量状态；
- 分析是否就绪、等待还是过期；
- 当前筛选条件，以及如何清除/复制/分享该视图。

这不要求做成固定的“状态条”，也不要求每页显示所有字段，但信息不能藏在只对开发者有意义的编号或悬停提示里。

### 3.3 渐进披露

先给用户完成当前任务所需的最小信息，再让其展开证据、计算口径、版本详情和原始来源。复杂表单、规则版本、邮件调度和运维摘要均应分层；不要在首屏一次性倾倒所有高级字段。

渐进披露不是隐藏风险：阻断异常、缺失来源、未发布、过期和权限限制必须在摘要层可见，并提供明确的详情入口。

## 4. 关键用户旅程

### 4.1 首次进入与登录

**目标**：安全进入系统，同时不让用户误解系统是否已初始化。

- 未初始化时只进入首个管理员创建流程；创建成功后建立会话，并明确该入口不会再次开放。
- 已初始化时进入登录；账号不存在、密码错误、账号禁用和暂时锁定使用安全的通用失败语义，不泄露账号存在性。
- 支持密码管理器、粘贴和显示/隐藏密码；登录提交期间按钮给出进行中状态，失败后保留可修正输入并把焦点带到可行动的错误位置。
- 登录成功后优先回到用户原本想去的深链页面；若没有，则进入公司总览。退出后清除会话并回登录，不把已缓存的业务数据留在可见界面。

### 4.2 公司总览：从结论到解释

**目标**：管理层在几十秒内判断“现在能不能用、哪里需要关注”。

首屏信息层级建议是：

1. 数据截至日与整体质量/覆盖结论；
2. 净资产合计、产品覆盖、公司日收益、公司指数、开放风险等核心摘要；
3. 产品级异常或未就绪清单，优先显示需要行动的项目；
4. 趋势与比较；
5. 进入产品、风险或导出的下一步。

总览只读取活动产品的已发布版本。未发布版本、待复核版本和原始导入数据不能混入 KPI（关键指标）数字；分析 `pending`（等待）或 `stale`（过期）时，数字旁应明确标注“数据已发布，但分析尚未覆盖当前版本”，而不是显示一个看似完整的空值或旧值。

用户从风险数、产品行或覆盖率进入下一级时，筛选条件应被保留并可返回；不要让一次点击丢失上下文。

### 4.3 产品列表与产品详情：比较后再深入

**目标**：先定位产品，再理解单个产品的净值、持仓和质量。

产品列表默认用于扫描和比较：名称、代码、估值日、单位净值、日收益、质量、分析状态和产品状态应能快速对齐；搜索、状态和估值日筛选要能组合、清除、分享和恢复。空结果要说明“当前筛选无匹配”，而不是与系统无数据混淆。

产品详情要保持产品身份和当前估值上下文：

- 净值序列强调时间范围、数据粒度、指标来源和缺失日期；不要用连续线条暗示缺失数据是零或每日都有估值；
- 持仓强调估值日、排序口径、市场/账户可能为空，以及数据是否为已发布快照；
- 数据质量强调规则、级别、实际值、期望值、差异、消息和来源位置；用户可从摘要进入具体异常；
- 资产配置、份额每日数据、版本差异等只有在有真实页面数据接口时才能成为结构化页面能力；仅有 CSV（逗号分隔文件）导出时，应把它表达为导出任务，不能伪装成页面实时查询。

### 4.4 导入：把不确定性变成可处理队列

**目标**：业务员知道文件到了哪里、系统正在做什么、自己何时需要介入。

建议把导入理解为“批次工作区”，而非单纯上传框：

1. 选择来源（手工上传、邮件附件或历史迁移的结果）并说明允许的 `.xls`/`.xlsx`（Excel 文件格式）；
2. 上传前即时显示文件名、大小、格式和重复提示，避免上传后才发现低级错误；
3. 批次提交后显示接收、排队、解析、校验、完成或失败的阶段；后台处理期间用户可以离开页面，回来后仍能从批次列表恢复；
4. 每个文件可看到哈希、重复标记、关联版本、任务状态和错误编号；
5. 技术失败提供受控重试，业务校验异常引导去复核或修正配置，不提供无限重试和“忽略全部”；
6. 非估值表、重复文件、产品/日期未决和同日内容冲突要用不同的结果语义，解释系统为什么没有发布；
7. 原始文件下载是受权限、批次关联和路径约束保护的证据操作，应在来源上下文中出现并写入审计。

批次级进度可以汇总，但不能用一个“处理中”覆盖已经失败、重复或待复核的文件。批量操作必须允许用户查看成功、跳过和失败的分项结果。

### 4.5 异常复核与发布：证据驱动的决定

**目标**：用户在理解异常后作出可追溯决定，不把人工忽略变成静默绕过。

复核工作区应按“待处理优先”组织，并清楚区分：

- **阻断级**：不能直接发布，需人工决定；
- **警告级**：版本可发布，但需明确确认；
- **提示级**：提供上下文，不应夺走阻断异常的注意力。

每条发现至少需要显示规则含义、实际值、期望值/容差、差异、消息、估值日、产品、版本、原始文件和来源位置。来源位置是线索，不等于可编辑原文；不要承诺从页面直接定位到不存在的 Excel 单元格预览。

发布、驳回、撤回、恢复和“发布并忽略”必须满足：

- 动作对象和当前状态明确；
- 必要时填写原因/复核意见；
- 警告确认明确说明“这条异常会被记录为人工忽略”；
- 发布新版本会替代同产品同估值日的旧已发布版本，并说明会触发分析；
- 并发冲突或状态已变化时，以服务端事实为准，提示刷新后重新判断；
- 批量发布显示快照范围、成功数、失败数和逐项失败原因，不能假设全部成功；
- 完成后刷新服务端状态，给出下一步入口（查看产品、查看任务或继续处理）。

### 4.6 风险：从触发到处置

风险事件是后端基于已保存指标和风险规则产生的事实，不是用户在页面上手工计算的结论。列表应支持按产品、估值日、严重度和处理状态筛选，并让用户一眼区分待处理、已确认、已解决和已忽略。

处理表单要收集处理结果、处理意见和可选证据引用；结果不能只靠颜色表达。已处理事件保留处理人、时间、最后触发时间和证据摘要。忽略不是删除，也不是修正指标；文案应避免把它表达成“风险不存在”。

### 4.7 邮件接入：设置与运行分离

**目标**：管理员安全维护连接，业务员能看到同步是否正常并手动触发同步。

连接配置（主机、端口、账号、授权码、自动同步开关和调度）与运行记录（运行编号、状态、消息/附件统计、失败编码）应分开理解。授权码永不回显、永不写入浏览器存储和日志；更新成功后输入应清空。

连接测试、立即同步、暂停/恢复自动同步都有进行中、成功、失败和重试路径。邮件同步失败应把网络、DNS（域名解析）、TLS（安全连接）、凭据不可用和未配置等可行动原因翻译成用户能处理的提示，不显示敏感细节。

### 4.8 目录、规则与系统管理：低频高影响

配置页面的核心不是“表格可编辑”，而是让用户知道配置何时生效、作用范围是什么、会影响后续哪些导入或分析。

- 产品名称、产品代码、别名、份额类别、科目映射和风险规则都是人工维护口径，页面要明确这一点；
- 规则和映射的修改优先表达为新版本/新有效期，而不是覆盖历史；
- 启用、停用、禁用账号、改角色和重置密码说明影响范围，并要求必要原因；
- 审计日志只读、不可删除，展示脱敏摘要、操作人、动作、资源、结果和原因；
- 系统设置区分当前值、来源和生效语义；
- 数据保留必须“先预演、后执行”。预演显示候选数、计划数、跳过原因和安全检查；执行要求固定确认短语与原因，并明确数据库标准化数据和审计不会被清理。设计不能提供模糊的“一键清理全部”。

## 5. 数据状态与反馈语言

### 5.1 三条状态轴

不要把以下三件事合成一个颜色或一个标签：

1. **版本生命周期**：已接收、解析中、校验中、可发布、待复核、已发布、已替代、已驳回、失败、重复、非估值表、已作废；
2. **质量判断**：有效、部分覆盖、警告、过期、处理中；
3. **分析进度**：就绪、等待、过期，以及必要时的失败。

用户不需要知道枚举英文名，但需要知道它们对当前操作的含义。例如：“已发布 + 分析过期”意味着可查看已发布估值，但风险/汇总分析可能尚未覆盖最新版本；“校验中”意味着不能把当前文件当作已发布数据使用。

### 5.2 状态文案规则

- 用“事实 + 影响 + 下一步”，例如“已接收，正在解析；完成后会进入校验”或“分析仍在排队，当前页面显示上一轮已就绪结果”；
- 失败说明原因类别、对象、是否改变数据、是否可重试；
- 空状态区分无数据、无匹配、无权限、尚未完成配置和暂时不可用；
- 成功反馈说明完成了什么，不只说“成功”；
- 警告和危险操作不使用夸张、责备或含糊语气；
- 所有时间、日期、金额、净值和比例遵循统一格式；缺失值显示“未提供/暂无”，不显示为 0；
- 关键数字同时提供文字语义，颜色不能承担唯一含义。

### 5.3 加载、轮询与实时感

后台任务可能持续较久，设计应使用稳定的阶段反馈、骨架或进度摘要，避免空白页面和频繁跳动。轮询更新不应抢走焦点、重置筛选或把用户正在阅读的抽屉关闭。计数变化需要上下文提示，例如“待复核增加 2 个版本”，而不是只让一个红点无声变化。

## 6. 交互边界与设计自由度

### 6.1 必须保持的边界

- 后端权限是最终安全边界；前端隐藏按钮不能被当作授权机制；
- 未发布、待复核、失败或重复数据不得混入看板的已发布结果；
- 已发布、已替代、已作废版本及标准化明细不可就地修改；修订必须产生新版本并保留历史；
- 任何可能改变发布可见性、规则口径、账号能力或文件保留的动作都要有确认、原因和审计语义；
- 不从证券代码、名称、常识或文件名猜测市场、账户、产品身份或指标口径；
- 不把偶然字段包装成外部基准、交易归因、流动性或合同限额判断；
- 不能用模拟数据、静态卡片或假接口掩盖后端没有提供的能力；
- 导出是文件操作，不等同于页面查询；下载原始文件必须受控并可审计；
- 失败重试只能用于明确的技术失败；不能给业务校验提供无限重试或一键绕过；
- 不删除用户可见的历史证据来“清理界面”。

### 6.2 可以自由探索的部分

设计师可以自由决定：

- 工作台、侧栏、顶部导航、分栏、时间线、抽屉、详情页或其他信息架构表达；
- 页面如何把“结论→证据→动作”组织在同一视野内；
- 品牌、字体、色板、密度、圆角、阴影、图表风格和空状态插画；
- 是否使用键盘快捷操作、命令面板、批量选择、保存视图、面包屑或最近访问；
- 在不改变语义的前提下把多个现有页面合并为工作区，或把复杂配置拆成向导；
- 在真实数据接口允许的范围内，为相同信息提供列表、图表、表格和导出等不同表达。

自由探索的前提是：用户仍能看见状态、来源、影响、权限和下一步，且操作不会破坏版本不可变、审计和后端状态机。

### 6.3 不宜在 UX 文档中写死的内容

本指南刻意不规定具体组件名称、页面像素、栅格列数、按钮所在角落、固定品牌色值、必须使用某个 UI 框架、必须采用某一种图表库或必须保留当前页面名称。这些属于实现与视觉设计层，应由设计师结合可用性测试、品牌和技术约束决定。

## 7. 数据展示与图表原则

- 图表服务于比较、趋势和异常定位，不服务于装饰；
- 时间序列标明时间粒度、范围、缺失和指标来源；缩放或筛选后仍能恢复完整范围；
- 图表旁提供精确数值、文字摘要或可排序数据表；悬停不是唯一的访问方式；
- 颜色之外使用标签、线型、形状、位置或文字说明表达差异；避免只用红/绿区分好坏；
- 资产配置类别较多时优先考虑可比较的条形/表格表达，不滥用饼图；
- 大量持仓、审计和导入记录优先保证分页、排序、筛选和列可读性；
- 金额、比例、净值和日期使用本地化格式，但保留足够精度和单位说明；
- 数据不足时诚实显示不足原因，不通过插值、补零或视觉连续性制造确定性；
- 导出内容应与当前筛选和用户权限一致，并在触发下载时给出明确反馈。

## 8. 表单、确认和错误恢复

### 8.1 表单

- 每个字段有可见标签；占位符只能补充示例，不能替代标签；
- 相关字段分组，复杂选项渐进展开；只读与禁用要有不同语义；
- 常规字段在失焦后校验，提交失败时保留输入；
- 多错误表单在顶部提供可聚焦的错误摘要，同时保留字段旁的具体错误并支持跳转；
- 校验文案包含原因和修复方向，避免只写“格式错误”；
- 长表单关闭时提示未保存内容；若采用草稿，明确草稿与已生效状态；
- 涉及密码、授权码和确认短语时支持粘贴、密码管理器和显示/隐藏，不在日志或浏览器存储中保留敏感值。

### 8.2 确认分级

不是每个按钮都弹确认框。建议按后果分级：

- 普通查询/筛选：即时执行，可撤销筛选；
- 可重复且低风险写操作：提交时给进行中和成功反馈；
- 发布、撤回、驳回、批量发布、改角色、禁用、规则停用：确认对象、当前状态、影响范围和原因；
- 原始文件清理：预演、固定确认短语、原因、结果摘要，必要时要求二次确认；
- 不可恢复动作：除非后端确实支持，否则不要设计“删除”或承诺撤销。

### 8.3 错误恢复

错误反馈至少回答：发生了什么、哪些数据改变了、用户现在能做什么。网络超时提供重试；状态冲突提供刷新并保留用户上下文；权限错误说明需要何种角色或联系人；后台失败提供错误编号和操作路径；字段错误定位到字段。Toast（短暂提示）只能补充反馈，不能承载唯一错误说明或替代表单错误。

## 9. 无障碍、响应式与性能

这些是体验要求，不是“最后再补”的实现细节：

- 正常文字对比度至少 4.5:1，非文字状态和焦点边界有足够对比；
- 所有交互可用键盘完成，焦点始终可见，路由切换后焦点进入主内容；
- 图标按钮有可访问名称，装饰图标不进入阅读顺序；状态变化用有上下文的 `aria-live`（辅助技术播报区域），不让每个数字都抢播报；
- 表格支持语义表头、排序状态和窄屏下的可读替代；图表提供文字摘要和表格替代；
- 触控目标至少约 44×44 CSS 像素，间距足够；鼠标悬停不是唯一交互方式；
- 支持 375px 窄屏、平板和宽桌面；不要求用户横向滚动整页，复杂表格可以在局部滚动或采用列优先级；
- 页面为加载、空、错误、部分覆盖和无权限状态预留稳定空间，避免布局跳动；
- 动效短、克制、表达因果；遵守 `prefers-reduced-motion`（减少动态效果偏好），数据应在无动效时立即可读；
- 大数据集分页或分段加载；轮询、图表和下载不阻塞主操作；
- 不使用 emoji（表情符号）作为结构性图标，不依赖模糊渐变、透明玻璃或低对比灰字传达层级。

## 10. 研究与验收方法

### 10.1 建议测试任务

用真实或脱敏数据测试以下任务，而不是只看静态稿：

1. 只读用户确认“截至某日哪些产品可用”，并进入一个分析尚未就绪的产品；
2. 业务员上传一个正常文件、一个重复文件和一个有警告的文件，分别说出下一步；
3. 业务员从待复核队列查看阻断异常、定位来源并发布或驳回；
4. 业务员处理一个风险事件并保留证据引用；
5. 管理员修改一个规则版本、禁用账号、测试邮件连接并查看审计；
6. 管理员执行原始文件清理预演，解释为什么某些文件被跳过；
7. 模拟网络失败、任务失败、并发状态变化和会话失效，观察用户是否能恢复。

### 10.2 设计交付至少应包含

- 角色与主要任务地图；
- 关键旅程和状态流转；
- 正常、加载、空、部分覆盖、失败、无权限、过期和冲突状态；
- 发布/复核/清理等高风险动作的确认与恢复说明；
- 数据可信度、来源和分析状态的表达方案；
- 键盘/屏幕阅读器/窄屏验收说明；
- 页面与真实 API 能力的映射，明确“已支持”“仅导出”“暂不提供”；
- 仍需通过产品或业务负责人确认的开放问题，而不是擅自把假设写成规则。

### 10.3 交付前检查清单

- [ ] 用户能在首屏区分已发布、处理中、待复核、分析过期和请求失败。
- [ ] 每个高影响操作都显示对象、范围、后果、原因和审计语义。
- [ ] 从异常到证据到决定再到结果的路径无需记忆编号或重复筛选。
- [ ] 缺失值、覆盖率、日期范围和指标来源没有被视觉连续性掩盖。
- [ ] 只读角色能顺畅查看结果，且不会看到无法执行的写操作。
- [ ] 所有错误都有可行动的恢复路径，批量操作有逐项结果。
- [ ] 图表有精确值、文字摘要和表格/键盘替代。
- [ ] 键盘焦点、错误摘要、动态播报、对比度和窄屏布局已验证。
- [ ] 文案没有越过产品范围，把未提供的能力说成已实现。
- [ ] 页面结构仍保持设计自由，没有把具体组件、像素和框架当成产品规则。

## 11. 待确认问题

以下问题会影响下一版体验，但当前代码和长期文档不能替业务负责人回答，设计稿应保留决策位：

- 公司总览默认显示最新可用日，还是由用户选择一个统一估值日？节假日和产品不同步如何解释？
- “警告可发布”的职责边界、批量发布的审批要求和双人复核是否需要扩展？
- 分析排队或过期时，是否允许继续看上一轮结果？若允许，如何在业务上标注其适用范围？
- 原始文件的保留期限、备份完成定义和清理审批是否需要更细的组织流程？
- 风险事件的处理状态是否需要负责人、截止时间、评论历史或通知？
- 产品策略、管理人、市场/账户等人工元数据由谁维护，何时生效，如何影响历史版本？
- 是否需要为管理层生成固定周期报告，或现有 CSV 导出已足够？

在这些问题得到确认前，设计应采用可解释、可追溯、可回退的默认行为，不用视觉设计替业务规则做决定。
