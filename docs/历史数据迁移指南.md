# 历史估值数据迁移指南

本文是把本地历史估值目录导入生产系统的唯一操作说明。迁移工具只读源目录，使用与盘点工具相同的产品、表内估值日期和 SHA-256（安全哈希）去重口径，再通过正式导入接口上传；它不另行解析 Excel（电子表格），也不直接写生产数据库。

## 2. 迁移前置条件

迁移前必须具备：

1. 生产数据库已执行最新 Alembic（数据库迁移工具）迁移。
2. 已通过 `POST /api/v1/auth/initialize`（初始化接口）创建第一个管理员。
3. 已用 `deploy/bootstrap.example.json`（初始化配置模板）配置产品、别名、份额类别、科目映射和风险规则。
4. 服务端原始文件目录可读写，且生产 API、worker 和数据库均健康。
5. 迁移操作使用 `admin`（管理员）或 `operator`（业务员）会话；命令行迁移工具从 `MIGRATION_TOKEN`（迁移会话值）读取登录后 `fund_session` Cookie 的原始值，并按正式 API 的 Cookie 认证契约调用导入接口。
6. 清单和报告输出在历史源目录之外，并预留临时空间。源目录和生产原始文件卷不在本次文档整理中删除。

`MIGRATION_TOKEN` 只应通过当前登录会话临时注入进程环境，不要写入仓库、清单、报告或命令历史。它不是 Bearer（令牌授权）令牌；迁移工具会把它作为 `fund_session` Cookie 发送。会话失效后应重新登录并重新注入，不要把长期密码交给迁移工具。

## 3. 生成和检查清单

在能访问历史目录的 Windows（操作系统）机器上，从仓库根目录执行：

```powershell
Set-Location F:\AgentWorks\基金分析看板
\.venv\Scripts\python.exe -m app.migration `
  --root "F:\AgentWorks\估值表A" `
  --manifest "F:\AgentWorks\基金分析看板\artifacts\migration-manifest.json" `
  --report "F:\AgentWorks\基金分析看板\artifacts\migration-report.json" `
  --dry-run
```

预演会递归读取文件、计算哈希、解析估值表并写清单/报告，不创建服务端批次，不上传，不移动或修改源文件。输出路径不能位于源目录内。重点检查：

- `action=import`（导入）和 `action=import_gz_only`（仅归档目录补充）是否为预期文件；
- `action=needs_review`（需要复核）是否只有人工可解释的冲突或识别问题；
- `skip_duplicate`（跳过重复）是否为同产品、同日期、同哈希的副本；
- `skip_non_valuation`（跳过非估值）是否包含交易记录和其他非估值文件；
- 清单中的 `root_name`、相对路径、大小和哈希是否与源目录一致。

清单状态包括 `pending`（待上传）、`uploaded`（已上传）、`failed`（上传失败）、`needs_review`（待人工复核）和 `skipped`（已跳过）。清单是断点续传状态文件，不应手工改变文件识别字段或状态；如果源目录发生变化，应删除/重新生成清单的工作副本并重新预演，而不是强行续传旧清单。

## 4. 业务目录初始化

复制并编辑配置模板。生产配置应放在服务器受控目录，不进入 Git（代码库）：

```bash
cp deploy/bootstrap.example.json /etc/fund-dashboard/bootstrap.json
chmod 600 /etc/fund-dashboard/bootstrap.json
```

先预演，再正式执行：

```bash
docker compose --env-file deploy/.env -f deploy/compose.prod.yml \
  run --rm --no-deps \
  -v /etc/fund-dashboard/bootstrap.json:/run/bootstrap/bootstrap.json:ro \
  -v /etc/fund-dashboard/migration:/run/migration:ro \
  api python -m app.bootstrap \
  --config /run/bootstrap/bootstrap.json --dry-run

docker compose --env-file deploy/.env -f deploy/compose.prod.yml \
  run --rm --no-deps \
  -v /etc/fund-dashboard/bootstrap.json:/run/bootstrap/bootstrap.json:ro \
  -v /etc/fund-dashboard/migration:/run/migration:ro \
  api python -m app.bootstrap \
  --config /run/bootstrap/bootstrap.json
```

`bootstrap`（业务目录初始化）会检查数据库表、服务端存储目录、迁移清单格式和清单中的产品标签。它不读取历史 Excel 内容，也不接收管理员密码。已有业务目录时默认停止；确认是受控补充后，才使用 `--allow-existing`（允许合并已有目录）。相同配置重复执行是幂等的，配置发生变化必须重新预演并保留审阅记录。

建议初始配置：

- 产品标准名称使用 Excel 中实际出现的名称；
- 将历史目录名、文件名或工作表中出现的别名登记到产品别名；
- 先配置少量已确认的科目映射，导入样本后再扩展；
- 风险规则阈值必须由业务负责人确认，不能从历史异常反推为默认阈值。

## 5. 样本迁移和验收

不要一开始就上传全部候选。建议先从每个产品选取：一个普通日期、一个有份额数据的日期、一个有持仓数据的日期，以及一组待复核冲突文件。

样本上传方式：

```powershell
\.venv\Scripts\python.exe -m app.migration `
  --root "F:\AgentWorks\估值表A" `
  --manifest "F:\AgentWorks\基金分析看板\artifacts\migration-manifest.json" `
  --report "F:\AgentWorks\基金分析看板\artifacts\migration-report.json" `
  --base-url "https://fundscope.example.com" `
  --workers 1
```

正式上传模式会：

1. 创建一个 `migration`（历史迁移）导入批次；
2. 每个文件上传前重新检查相对路径、文件存在性、大小和 SHA-256；
3. 每个文件完成后立即写回清单，单文件失败不会阻断其他文件；
4. 所有可上传文件成功后调用批次完成接口；
5. 生成迁移报告，供后续核对和续传。

正式上传前，在当前 PowerShell（Windows 命令行）进程临时设置登录后 `fund_session` Cookie 的原始值；不要把真实值写进脚本或提交到代码库：

```powershell
$env:MIGRATION_TOKEN = "从登录响应的 fund_session Cookie 读取的临时值"
\.venv\Scripts\python.exe -m app.migration `
  --root "F:\AgentWorks\估值表A" `
  --manifest "F:\AgentWorks\基金分析看板\artifacts\migration-manifest.json" `
  --report "F:\AgentWorks\基金分析看板\artifacts\migration-report.json" `
  --base-url "https://fundscope.example.com"
Remove-Item Env:MIGRATION_TOKEN
```

上传模式在缺少该环境变量时会直接停止，不会创建远程导入批次。

样本验收至少包括：导入批次状态、版本产品和日期、阻断/警告校验、原始文件受控下载、看板不可见未发布数据、发布后分析任务是否完成，以及产品详情净值/持仓/质量页面是否可读。样本未通过前不要批量发布。

## 6. 冲突处理和批量迁移

同日不同哈希文件会被标记为 `needs_review`，不会自动上传为可发布的估值候选。业务核对时应同时查看：表内估值日期、产品身份、总资产/负债/净资产、净值、持仓和原始文件来源。选择结论应记录在外部业务审阅记录中；本工具不替业务判断，也不改写清单为自动选择。

确认配置和样本后，使用同一份未被源目录变化破坏的清单继续上传。`--workers` 只控制本地盘点扫描并发；在 2C4G（2 核 4 GB）生产服务器上，服务端 worker 默认串行处理数据库任务，不应通过增加上传并发掩盖服务端队列积压。

导入全部主目录候选后，按产品和日期核对：

- 主目录预期覆盖日期和法定节假日/非交易日缺口；
- 版本状态、校验严重度、失败任务和待复核数量；
- 每个产品的最新发布日、净值序列和公司总览覆盖数；
- 资产配置和持仓中的科目映射命中情况；
- 生产源文件卷、数据库卷和备份卷剩余空间。

只有经过抽样核对的版本才允许通过复核队列发布。发布新版本会替代同产品同日期的旧已发布版本，并触发后台分析；分析任务失败不会自动回滚发布状态，应按运行手册处理。

## 7. 失败恢复

- `pending` 或 `failed` 的上传项：先检查网络、权限和源文件是否变化，再使用原清单续传。
- 批次处理失败：在导入页面或 `POST /api/v1/imports/{batch_id}/retry`（重试接口）执行受控重试；业务校验异常不是无限重试理由。
- 产品/日期识别不正确：修正产品别名或配置后重新建立清单；不要直接改数据库版本。
- 校验阻断：保留原始文件和失败版本，核对表格内容与映射规则后，再通过新导入版本修订。
- 分析失败：查看运维摘要、任务错误编号和 worker 日志；修复代码/配置后重新触发受控版本生命周期，不手工修改指标表。

迁移工具不删除源目录文件，也不删除服务端数据库记录。迁移清单和报告属于可重新生成的工作产物，不应提交到代码库。

## 8. 工具边界

迁移只使用以下真实数据：Excel 工作簿内可识别的产品、估值日期、汇总、份额、科目和持仓字段，以及人工维护的产品别名和科目映射。它不能产生外部基准、交易归因、行业穿透、流动性天数、VaR（风险价值）或合同限额结论。

更详细的扫描规则见 [历史文件盘点工具说明](../tools/valuation_inventory/README.md)；上线后的任务、备份、清理和恢复见 [生产运行手册](runbook.md)。
